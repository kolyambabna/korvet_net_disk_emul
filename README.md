# Сетевой монитор КОРВЕТ CP/N-90 — Python-порт (`pcndr.py`)

**Версия: 1.01p** · Кроссплатформенно: Linux / Windows · Python ≥ 3.8

Функциональный аналог сетевого монитора `NDR` из комплекта сетевой ОС
**CP/N-90** (корветовские классы КУВТ). Монитор эмулирует сервер сети по
последовательному порту и позволяет:

* **сетевой загрузить CP/M** в Корвет-РМУ (ПК8010 без дисководов, либо ПК8020
  в режиме РМУ) — первичным загрузчиком и образом клиентской системы;
* **эмулировать сетевые диски A:, B:, E:** по образам формата **KDI** — чтение
  как в оригинальной C-версии, запись (создание/закрытие файла, удаление,
  переименование) добавлена этим портом;
* обслуживать запросы сетевой CP/M: чтение абсолютных секторов, последовательное
  чтение файлов, открытие/закрытие/создание/переименование/удаление, запись
  файлов прямо в образы KDI.

Оригинал на C: `main.c`, `std_lan.c`, `kdi.c` (автор — Alexander Stepanov
aka `forth32`, forth32@mail.ru). Общий обзор системы, подключение Корвета
переходником TTL↔RS-232/USB, цоколевка разъёма XS5 и установка сетевого адреса
перемычками — в [корневом README проекта](../README).

## Быстрый старт

1. Установить зависимости (нужна только `pyserial`):

   ```bash
   pip install -r py/requirements.txt
   ```

2. Проверить, что в **текущем каталоге** (корень проекта) есть системные файлы:
   `cpn90ldr.bin`, `cpn90img.bin`, `cpn90sys.bin`, а образы дисков — в `disk/`.

3. Подключить Корвет (см. [корневой README](../README)): переходник уровней
   сигнала к разъёму XS5, перемычки A0–A3 задают адрес РМУ (по умолчанию
   монитор рассчитывает на **адрес 2** — замкнутая линия A1).

4. Запустить монитор **из корня проекта**:

   ```bash
   # Linux
   python py/pcndr.py -a disk/sys.kdi -b disk/ESL_12.kdi -s /dev/ttyUSB0

   # Windows
   python py\pcndr.py -a disk\sys.kdi -b disk\ESL_12.kdi -s COM3
   ```

5. Перевести Корвет в ROM-Бейсик (он включается сам, если назначен адрес ≠ 0) —
   монитор сам пошлёт загрузчик и образ системы, после чего можно запускать
   программы с сетевого диска `A:`.

Имя последовательного устройства в Linux видно в `dmesg` после подключения
переходника (`/dev/ttyUSBx` или `/dev/ttyACMx`).

## Ключи командной строки

Совместимы с C-версией; добавлены отладочный ключ `-d` и два ключа режима
подтверждений (`-yy`, `-posty`) — см. предупреждение ниже.

| Ключ | Арг. | По умолчанию | Назначение |
|------|------|--------------|------------|
| `-a` | файл | `disk/sys.kdi` | образ KDI для диска **A:** (обязателен, иначе — аварийный выход) |
| `-b` | файл | *(пусто)* | образ KDI для диска **B:** |
| `-e` | файл | *(пусто)* | образ KDI для диска **E:** |
| `-s` | устр. | `/dev/ttyS0` | последовательный порт: `/dev/ttyS0`, `/dev/ttyUSB0`, `COM3`, … |
| `-n` | 1–15 | `2` | адрес РМУ, заданный перемычками A0–A3 (диапазон проверяется) |
| `-x` | — | — | пропустить загрузку системы (ОС уже в РМУ, напр. после выхода из монитора для смены диска) |
| `-d` | — | — | отладочная печать сетевого обмена (`@`-строки: адресация, пакеты, передачи) |
| `-yy` | N | `1` | сколько байтов подтверждения подряд слать в ответ на пакет (и `'N'` тоже); на USB-RS232 переходниках нужно `2` |
| `-posty` | мс | `2` | пауза после подтверждения, перед ответом и следующим маркером опроса |
| `-h` | — | — | справка |

Параметры порта жёстко фиксированы, как в оригинале: **19200 8O1**
(8_data, odd parity, 1 stop), без аппаратного/программного flow control.
Таймаут ожидания байта из сети — 0,1 с (в C — `VTIME=1`).

> ⚠️ **Если ответы доходят с задержкой или теряются** (Корвет молчит, в логе
> одни и те же пакеты по нескольку раз) — виноват не протокол, а драйвер
> USB↔RS-232 переходника: одиночный байт `'Y'` «залипает» в его буфере до
> срабатывания latency timer (у CH340/PL2303 по умолчанию 16 мс) и не успевает
> в таймаут клиента. Лечится либо Latency Timer = 1 мс в Диспетчере устройств,
> либо `-yy 2` — несколько байтов подряд драйвер выталкивает сразу:
>
> ```bash
> python pcndr.py -a disk\sys.kdi -s COM5 -n 2 -yy 2 -posty 20
> ```
>
> `-posty` сам по себе от залипания не спасает (дело в драйвере до отправки),
> но даёт клиенту долю миллисекунд на обработку подтверждения.

## Клавиши управления во время работы

| Клавиша | Действие |
|---------|----------|
| `r` | повторная загрузка ОС в Корвет (напр. после Reset на РМУ) |
| `x` | выход из монитора (аналогично Ctrl+C) |

Реализация — [`console.py`](console.py): в Windows через `msvcrt` (работает
в обычном окне cmd/PowerShell/Terminal), в Linux/macOS терминал переводится в
cbreak-режим и восстанавливается при выходе. Если stdin перенаправлен (не
терминал), клавиши недоступны — выход по Ctrl+C.

```text
 $ python py/pcndr.py -a disk/sys.kdi -b disk/ESL_12.kdi -s /dev/ttyUSB0

 + Чтение каталога диска A
 + Чтение каталога диска B
 + Посылка загрузчика....
 + Посылка образа системы:  /
 + Загрузка системы окончена
 + Ждем команду от клиента
 + Открытие файла U0: A:PIP     COM
 + Запрос сектора: диск A дорожка 2 сектор 32
 + Чтение файла U0: A:PIP     COM - сектор 57     - Пересылка завершена
 + Создание файла U0: A:TEST    DOC
   + свободно блоков 160, входов каталога 79
 + Запись файла U0: A:TEST    DOC  блок # 12
 + Закрытие файла U0: A:TEST    DOC
   + записано 13 секторов (1664 байт), блоков 1, свободно ещё 159

   + помечено входов каталога: 1
```

Строка «Ждем команду от клиента» появляется сразу после загрузки — монитор
опрашивает сеть маркером и перехватывает запросы РМУ.

## Что происходит при запуске

1. Разбор ключей, проверка адреса РМУ (1–15).
2. Открытие порта `19200 8O1`, сброс буферов; формирование **маркера опроса**
   `FF 80|адрес`.
3. Открытие `cpn90sys.bin`, образов KDI; чтение каталогов всех заданных дисков
   (разбор инфосектора и записей с склейкой экстентов — `kdi.py`).
4. Без `-x`: посылка загрузчика `cpn90ldr.bin` (тип 7, адрес `0xEEEE`),
   задержка 200 мс, затем перекидка `cpn90img.bin` по 128 байт (88 секторов).
5. Главный цикл: отправка маркера → приём 34-байтного командного пакета →
   проверка КС (ответ `Y`/`N`) → диспетчер по коду функции → отклик сектором
   данных / содержимым файла / подтверждением.

Подробный формат всего, что летает по порту — [docs/PROTOCOL.md](docs/PROTOCOL.md).

## Эмулируемые диски

* **A:, B:, E:** — сетевые диски по образам KDI. Параметры файловой системы
  берутся из инфосектора образа (число секторов, размер блока, каталог);
  стандартная конфигурация CP/M — 2 системные дорожки, 128 записей каталога,
  блоки 2 КБ. Нестандартные образы (напр. от MICRODOS) не поддерживаются —
  как и в оригинале.
* При доступе с буквы **E:** в образе пропускаются 2 начальные дорожки
  (`SYSOFFSET[4] = 2`) — способ «разрезать» один большой образ на несколько
  дисков.
* **Чтение дорожек 0–1 диска A:** подменяется данными из `cpn90sys.bin` —
  так работает «тёплый рестарт» сетевой CP/M.
* **F:** — рамдиск в памяти ГЗУ, формируется клиентской частью на самой РМУ
  (монитор в нём не участвует). Перед использованием очистить `ERA F:*.*`.

## Запись файлов

В отличие от C-версии (где записываемые данные уходили в `tempfile.bin`, а
переименования и удаления логировались и игнорировались), Python-порт меняет
сами образы KDI:

| Операция клиента | Что делает монитор |
|------------------|--------------------|
| `22` создать файл | готовит сессию записи, печатает запас свободного места (блоки, входы каталога) |
| `21` блок данных | принимает 128 байт + **нарастающую** КС: `'Y'` — принят, `'N'` — отброшен, клиент повторяет блок |
| `16` закрыть файл | выделяет блоки, пишет данные и описатели каталога в образ |
| `19` удалить | помечает все экстенты файла `0xE5` — его блоки становятся свободными |
| `23` переименовать | правит имя во всех экстентах; отказ, если новое имя уже занято |

Файл копится в памяти и попадает в образ **только на закрытии** (`fn=16`):
обрванная передача, файл без закрытия (`- Клиент не закрыл файл, образ не
изменен`) или нехватка места (`- файл не записан: не хватает места…`) не
оставляют в образе ни лишних описателей каталога, ни частичных данных. Имена
нормализуются к FCB CP/M (8+3, старшие биты байт — атрибуты), запись идёт под
нулевую user-область. Раскладка блоков и экстентов —
в [docs/KDI.md](docs/KDI.md#6-запись-файлов-сверх-kdic), последовательность
обмена по протоколу — в [docs/PROTOCOL.md](docs/PROTOCOL.md).

Практический смысл: на сетевом диске работают `SAVE`, `PIP` с удалением, `ERA`,
`REN`. Разумный порядок действий с образами всё тот же, что с дискетами:
монитор держит образ открытым на запись, поэтому копии оригинала никто не делает
автоматически.

## Отладка и диагностика

| Симптом | Что делать |
|---------|-----------|
| Порт не открывается | проверить имя (`-s`), права (`dialout` в Linux), что порт не занят терминалкой/модемом |
| Корвет не грузится, в логе тишина | адрес перемычками ≠ `-n`; нет согласования уровней TX/RX; проверить линию вызвонкой |
| Тот же пакет в логе по нескольку раз, клиент как будто не видит `Y` | одиночный байт подтверждения залипает в драйвере USB-RS232: запуск с `-yy 2` (или Latency Timer = 1 мс в свойствах порта) |
| `Пакет с неправильной контрольной суммой` | помехи на линии; уменьшить длину провода, включить `-d` и посмотреть стабильность адресации |
| `+ Передача данных: .....NNN` с буквами ошибок | РМУ не подтверждает пакеты; увеличить `ADR_DELAY` в `lan.py` |
| Загрузка «отваливается» на середине образа системы | медленный CPU/Python не успевает за 19200 — см. ниже про тайминги |

Ключ `-d` печатает `@`-строки адресации и передачи (аналог `dprintf` в C):
`@ Посылка адреса: OK`, `@ Послана команда отправки данных`,
`+ Передано N байт`.

> ⚠️ **Про тайминги.** Порт работает на 19200 бод; в C-версии байты пакета
> уходят с паузой 0,8 мс, и Python-порт честно сохраняет её
> (`BYTE_DELAY` в `lan.py`). Основной риск переноса — задержка реакции монитора
> на запрос (главный цикл на Python заметно «медленнее» C на слабом железе).
> На современном ПК/одноплатнике (RPi 3+ и выше) запас по скорости огромный;
> на очень старых/перегруженных машинах возможны таймауты опроса.

## Тесты

Тесты не требуют железа и даже `pyserial` (проверяют протокол и парсер KDI
через эмуляцию порта). Из корня проекта:

```bash
python -m unittest discover -s py/tests -v
```

Покрытие — 88 тестов, железо и `pyserial` не нужны.

`tests/test_protocol.py` (18) — протокол ОПТС 2.0 через эмуляцию порта:

* контрольная сумма пакетов (эталонные векторы);
* framing: синхробайт, мусор перед пакетом, таймаут, битая КС;
* структура пакета на проводе (синхро/длина/номер/тип/КС/CR);
* экранирование в D-пакете: `#`→`##`, `<0x20`/`0x7F` → `#<c+0x40>`,
  старший бит данных, ограничение `MAXLEN=0x58` (84 байта данных);
* `send_data` с подтверждением Y;
* синтетический KDI: разбор инфосектора, каталог со склейкой экстентов,
  постраничная выдача 24 секторов из блоков 1–2, «файл не найден»;
* отправка подтверждения (`pcndr.send_ack`) и ключи `-yy`/`-posty`: по умолчанию
  один байт, как в C; `-yy 2` кладёт в линию `YY`/`NN` и делает `flush`.

`tests/test_kdi.py` (70) — чтение и запись образов KDI; синтетические образы в
нём собираются по формулам [docs/KDI.md](docs/KDI.md), а не кодом `kdi.py`:

* инфосектор: все поля (значения нарочно разные — сдвиг любого смещения ломает
  разбор), все коды размера физсектора, производные `blocking`/`alsize`/
  `reserved`/`dirblocks`, позиция каталога на CHS-границе;
* `seek_chs` для одно- и двустороннего диска, доступ к записанным байтам по CHS;
* каталог: склейка экстентов (в том числе вперемешку с другим файлом), пропуск
  входов `0xE5`, маскирование бит атрибутов имени, «нет начального экстента»,
  обрыв каталога концом образа, повторный `read_dir`;
* чтение файла: генератор 128-байтовых секторов, остановка на `records` внутри
  блока, порядок блоков по каталогу, дополнение `0xE5` за концом образа,
  «файл не найден», последовательное чтение двух файлов;
* битые образы: инфосектор короче `0x20`, нулевые `spt`/`lspt`, нулевая
  единица распределения;
* карта выделения: `max_block()` по `dsm` и по размеру образа, `first_block()`
  не даёт выделить блок под каталогом (на `sys.kdi` — с блока 2), занятые блоки
  и свободные входы каталога;
* запись: чтение назад побайтово, раскладка описателя (`ex`, `rc`, `user`,
  номера блоков), многоэкстентный файл на 300 записей (3 входа, `rc`
  128/128/44), замена существующего файла с освобождением его блоков, пустой
  файл, дополнение короткой записи нулями, отсутствие коммита → образ цел,
  «не хватает места на образе» и «не хватает места в каталоге» → образ цел,
  плохие имена (управляющие символы, пустое), доведение имени до FCB;
* удаление и переименование: правки во всех экстентах, освобождение блоков,
  отсутствие файла, занятое новое имя, плохое новое имя;
* демо-диск `disk/sys.kdi`: геометрия (5 физ. секторов по 1024 байта,
  80 дорожек, 2 стороны), каталог из 35 файлов со склейкой многоэкстентных
  `BIOS DOC`/`POWER DOC`, побайтовая сверка всех файлов с образом, КС пересылки,
  чтение `PIP COM` (`JMP 04CE`), неизменность образа после чтений.
* запись в **копию** демо-диска: файл на 200 записей ложится в свободные блоки
  начиная с `first_block()`, все прежние 34 файла остаются побайтово целыми,
  удаление освобождает блоки, переименование работает, каталог остаётся
  «печатным» (`A-Z0-9 `), а сам `disk/sys.kdi` — неотличим от исходного.

Только KDI, без протокола:

```bash
python py/tests/test_kdi.py -v
```

### Посмотреть содержимое образа глазами

`py/kdi_extract.py` — ручной прогон того же `kdi.py` (без проверок и тестов):
раскладывает все файлы каждого образа в подкаталог с именем образа без
расширения (`disk/sys.kdi` → `disk/sys/`), имена — `ИМЯ.РАСШ` из FCB CP/M,
размер — ровно `число записей × 128` байт, то есть с хвостом последней записи,
как его видит сетевая CP/M:

```bash
python py/kdi_extract.py                    # все образы в disk/
python py/kdi_extract.py disk/sys.kdi       # конкретный образ
python py/kdi_extract.py -o c:\tmp disk     # распаковать в другой каталог
```

## Отличия от C-версии

* **Запись в образы KDI** — сверх оригинала: `fn=16/19/21/22/23` меняют файл
  образа (создание с приёмом по записям, удаление, переименование) вместо
  `tempfile.bin` и пустого лога. Коммит только на закрытии файла, поэтому
  прерванная передача образ не меняет; в C-версии эти функции только
  протоколировались.
* **Переносимость**: Windows + Linux (порт и клавиатуру инкапсулируют
  pyserial/`console.py`).
* **Ключ `-d`** — в C печатная отладка не включалась из командной строки.
* **Ключи `-yy`/`-posty`** — режим отправки подтверждения (пачка байтов + `flush`
  и пауза после него). Нужны из-за драйверов USB-RS232: одиночный `'Y'` не
  успевает дойти до клиента. На Latency Timer = 1 мс можно оставить `-yy 1`.
* **Валидации**: номер диска вне 0–4, адрес вне 1–15, битый инфосектор, короткий
  образ, нехватка места на образе/в каталоге — обработаны явно (в C это было UB).
* Сообщения на консоль РМУ кодируются в **cp866**.
* Сохранено «как есть» (в т.ч. оригинальные quirks — см.
  [PORTING.md](docs/PORTING.md)): байт-в-байт протокол, тайминги, тексты
  лога, подмена sys-дорожек, `SYSOFFSET`, чтение файлов по блокам формулами
  `readdir`.
